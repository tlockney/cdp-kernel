Life after deno jupyter §

Deno's kernel is two halves joined by thirteen ops, and both halves come apart cleanly. Re-joined over the DevTools Protocol, the same kernel now runs notebooks on Node and on Deno, and on Bun, workerd and celld through backends of their own.

Bottom line up front
Revised 2026-10-15 The study was first compiled on 2026-10-14, when cdp-kernel was a spike. It has since been released (@tlockney/cdp-kernel 0.4.0 on npm and JSR), and most of the next steps in §10 are done. The verdict held. Sections 03, 04, 05, 09 and 10 are updated to the project's state at that date, and §11 compares what the study predicted with what was built. The analysis in §01, §02 and §06–§08 is unchanged except where marked.

Extraction is not only possible; it is done, and released. In June 2026 Deno rewrote its kernel (denoland/deno#34083). The Jupyter wire protocol, ZeroMQ included, is now about 600 lines of plain JavaScript. Execution happens in a separate isolate driven by standard Chrome DevTools Protocol calls. Node, Deno and workerd all expose CDP through --inspect, so the kernel can be pulled apart and pointed at a different runtime.

cdp-kernel does that. It is a port of Deno's protocol half, hosted on Node or Deno, plus the Deno.jupyter display API and a replacement for the parts of Deno's module loader that notebooks lean on: TypeScript, npm: and jsr:. It passes a conformance suite derived from Deno's own Jupyter tests on Node 24 and 26 and Deno 2.9 and the latest 2.x, on Linux and macOS. A notebook written for deno jupyter, with Polars DataFrames, Vega-Lite, SVG and in-place display updates, gives the same outputs on both.

The other routes rank below it:

  • workerd works only with a hybrid design. Timers and I/O are forbidden outside a request. Built: cells run inside one long-lived request (§06).
  • Bun needs its own backend, because it speaks WebKit's protocol rather than CDP. Built: an in-process evaluator over a pipe (§07).
  • rusty_v8 or FFI buys nothing for an evaluator. FFI cannot reach the host's V8 isolate, and a rusty_v8 host means rebuilding most of deno_core.

Recommendation: package cdp-kernel as a standalone, runtime-neutral kernel. Treat CDP as the primary backend. Add backends for Bun and workerd only if you need them.

Outcome: all three were done. The Bun and workerd backends, and a third for celld that reuses the workerd driver, share the host, wire protocol, transformer and display module, as predicted. The CDP targets remain the most faithful; the in-process backends trade some REPL semantics and lose state on a busy-cell interrupt (§09).

01

What changed

Ryan Dahl's post of 2026-10-09 (deno.com/blog/cloudflare) moves the Deno team to Cloudflare.

  • The runtime gets about a year of monthly bug-fix and security releases, then development ends.
  • Deploy shuts down in six months.
  • JSR stays up, with its infrastructure moving to Cloudflare.
  • rusty_v8 is the one piece with a stated future: "We will continue supporting rusty_v8 and work toward integrating it into workerd." No timeline is given.

The joint Cloudflare post, by Dahl and Kenton Varda, frames the goal as making self-hosted workerd a first-class way to run Workers apps, with celld folded back in. Neither post mentions deno_core, notebooks, or Jupyter.

Revised: celld is usable now. cdp-kernel gained a celld target on celld 0.6.2, alongside workerd (§11).

On the community side, denoland/deno#36995 collects fork announcements: rjs, dodo, and one maintainer's planned conservative fork. Nobody has claimed the Jupyter kernel. The existing Node kernels are stale: tslab last released in mid-2024, IJavascript in 2021, and both depend on the native zeromq addon.

Sourcing The announcement terms come from the Deno post, which I read directly. The fork names, the Cloudflare post's wording, and the kernel release dates come from a research sweep. I did not re-open those sources, so treat them as reported, not verified.
02

Anatomy of deno jupyter in 2.9

Older write-ups describe a Rust kernel built on libzmq or the runtimed crates. That kernel is gone. PR #34083, "rewrite kernel in JS, drop zeromq/runtimelib deps" (merged 2026-06-01), left two isolates in one process:

  • Kernel isolate, cli/js/jupyter_kernel.js. It implements ZMTP 3.0 over Deno.listen TCP: the greeting, the READY command, and framing. On top of that sit the five Jupyter channels and HMAC signing via WebCrypto.
  • REPL isolate, cli/tools/repl/session.rs. Each cell is parsed as TSX by swc and transpiled with var_decl_imports, which turns static imports into awaited dynamic imports. It then runs through Runtime.evaluate with replMode.
  • The bridge, cli/ops/jupyter.rs. Thirteen Rust ops forward requests over channels. Nearly all are thin wrappers over CDP calls: evaluate, callFunctionOn, getProperties, globalLexicalScopeNames. The others are interrupt (terminate_execution), iopub and stdin plumbing, and two version strings.
  • Display, cli/js/40_jupyter.js. Deno.jupyter.display, md, html, svg, image, plus Symbol.for("Jupyter.display"). It is duck-typed JavaScript with four Deno-internal dependencies: inspectArgs, base64, readFileSync, and WebGPU.
03

The extraction: cdp-kernel

The spike was about 2,350 lines of TypeScript and plain ESM, plus about 1,500 lines of tests. It now lives in its own repository, tlockney/cdp-kernel, at about 6,700 lines plus 5,200 lines of tests, and is published to npm and JSR as @tlockney/cdp-kernel. The host runs on Node 24+ with native type stripping, or on Deno when installed from JSR. Its runtime dependencies are still esbuild and acorn (with acorn-walk). The kernel host and the target runtime are separate processes:

  • The host speaks Jupyter to the frontend.
  • The target runs your code.
  • The target is launched as node --inspect=127.0.0.1:0 runtime/bootstrap.mjs or deno run -A --inspect=… runtime/bootstrap.mjs. The same bootstrap file loads unchanged in both.

What was ported, what was new

  • Ported almost line for line:
    • the ZMTP greeting, READY command and framing, keeping Deno's hard-won libzmq interop fixes;
    • HMAC sign and verify, dropping forged messages;
    • the shell, control and stdin handlers;
    • completion via getProperties and globalLexicalScopeNames;
    • the is_complete scanner and the codepoint/UTF-16 cursor maths;
    • the whole display formatter, covering DataFrames, Vega, images, HTML/SVG elements and the display symbol.
  • Replaced: swc became esbuild (TS, TSX, enums, JSX, with a TS fallback for <T>x) plus an acorn pass that rewrites imports, import() and import.meta. On Node, Deno's module loader became a module.registerHooks resolver: it re-parents cell imports to the notebook directory and adds npm: (install on first use, one npm alias per range) and jsr: (mapped onto npm.jsr.io).
  • New:
    • the two-session interrupt;
    • the pipe/WebSocket ordering barrier;
    • synchronous prompt() across a process boundary;
    • crash guards;
    • a Deno.jupyter proxy on Deno targets;
    • an opt-in Deno compatibility namespace on Node.
  • Added since the spike (each has its own issue):
    • Jupyter comms and anywidget-style widgets, on every target (#9);
    • inspect_request tooltips and history_request (#10);
    • typings for the jupyter global (#11);
    • a notebook's deno.json import map, JSX settings and node_modules on Deno targets (#13);
    • an opt-in lockfile and serialized installs for npm:/jsr: (#14);
    • JupyterLab's visual debugger on Node and Deno targets, over CDP's Debugger domain (#18);
    • Bun, workerd and celld targets (#7, #8, #25), and Workers project bindings in env (#26).

The Deno namespace

On a Deno target, Deno.jupyter is a non-configurable getter that throws outside deno jupyter. The Deno global itself is configurable, though, so the bootstrap swaps in a Proxy that answers jupyter and forwards everything else. Existing notebooks run unchanged, and a jupyter global is available everywhere.

On Node, --deno-compat installs a separate kernelspec (cdp-node-deno). It provides a Deno namespace covering:

  • jupyter, version and build;
  • env, args, cwd and chdir;
  • text and binary file I/O, with Node errno codes mapped to Deno.errors.*;
  • readDir, stat, mkdir, remove, rename, realPath, and temp files and directories;
  • inspect, stdout and stderr.
Why opt-in Libraries detect Deno with typeof Deno !== "undefined". With a shim present they take their Deno code paths, which may call APIs the shim doesn't cover (Deno.serve, Deno.Command, Deno.openKv). APIs outside the shim are simply absent, so feature checks still return false instead of throwing. Turning it on by default is a one-line change if that trade suits you.

The ranking turns on one fact. Deno already did the separation, and the seam it chose (CDP) is a public, multi-vendor protocol. Every route that keeps that seam inherits Deno's REPL semantics almost for free. Every route that drops it has to rebuild them.

06

workerd as a target

The probe ran workerd 2026-09-30 (npm workerd@1.20260930.1) with --inspector-addr and --experimental, and gave the worker an UnsafeEval binding. It compared inspector evaluation against evaluation inside a fetch handler.

A notebook needs timers and I/O, so a workerd backend has to run cells inside a request. workerd marks that context with an IoContext.

The design that follows from the probe:

  • A driver Worker exposes POST /eval.
  • The host hoists each cell's top-level declarations onto globalThis (the tslab technique) and runs it through UnsafeEval.newAsyncFunction.
  • Display messages travel back in the response.
  • The inspector is used only for completion.

That is a new backend behind the same host, not a change to the protocol half. If "rusty_v8 in workerd" eventually lets Rust code reach workerd's inspector or isolate directly, an in-process variant becomes possible. Nothing public yet says that it will.

What was built

Revised. The workerd target (#8, #26) kept the probe's core idea, cells evaluated through UnsafeEval inside a request with declarations hoisted onto globalThis, and changed the rest:

  • One request, not one per cell. The host opens a single WebSocket to the driver Worker, and every cell runs inside that session's request. I/O objects, Durable Object stubs and pending timers then carry over between cells, which a POST /eval per cell would not allow. The cost is that the request never ends, so Workers' per-request CPU and duration limits don't apply.
  • No inspector. Output and display messages come back over the session in order. The driver is served on a Unix socket in a private directory, opened with a per-launch token.
  • Interrupt. A cell waiting on a promise is abandoned in place and state survives. A busy cell can't be reached, so workerd is stopped and restarts on the next cell, losing state.
  • Workers projects. With a wrangler config at or above the notebook, the driver runs on the project's own Miniflare, with its bindings in env and its main as worker.

celld (#25) runs the same driver Worker over the same session. It allows a plain global eval, so it needs no --experimental, and it listens on loopback TCP rather than a Unix socket.

07

Bun

Bun 1.4.0's --inspect speaks the WebKit Inspector Protocol. Probed directly:

  • Runtime.evaluate works.
  • const redeclaration is tolerated even without replMode, because of JSC's console semantics.
  • Top-level await is a SyntaxError.
  • awaitPromise is ignored.
  • Runtime.addBinding, globalLexicalScopeNames and terminateExecution do not exist.

A Bun backend would therefore evaluate in-process: wrap cells in async functions, hoist declarations, report output through a socket back to the host, and interrupt by restarting the process. The host, wire protocol, transformer and display module carry over unchanged.

Revised. The Bun target (#7) was built this way, with two refinements. Host and target exchange JSON lines over a pipe on fd 3, which only the host holds, so there is no port at all. And interrupt only restarts Bun for a busy cell; a cell waiting on a promise is interrupted in place and keeps its state. The hoisting has visible edges: a top-level const can be reassigned, and declaring a global's name replaces that global instead of shadowing it.

08

rusty_v8 and FFI surfaces

Probed on this machine. Deno.dlopen (Deno 2.9.6) and bun:ffi (Bun 1.4.0) both loaded libSystem and called getpid(). Node 26.8.1 has a node:ffi module only behind --experimental-ffi. Without the flag, it is an unknown built-in, so the research sweep's "on by default" was wrong for this version. With the flag, dlopen worked. So one C-ABI library can be loaded by all three runtimes.

What FFI can't do is the important part. A kernel's evaluator has to run code in the host runtime's own isolate. A cdylib that links rusty_v8 brings a second V8 with its own heap. It cannot see the host's globals, modules, or node_modules. FFI is useful only for the transport, and the transport is already solved in pure JS. runtimed's pure-Rust jupyter-zmq-client (reported by the sweep, not opened) is a good reference implementation, but it isn't needed.

rusty_v8 as the base of a standalone kernel binary is coherent but expensive. The v8 crate has complete inspector bindings. You would still build an event loop, a module loader with TS transpile and npm: resolution, console, timers and fetch, which is most of what deno_core is. deno_core is still shipping releases (0.412 in September, per the sweep), but nobody has committed to its future. The CDP route reaches a richer result by borrowing an existing runtime instead.

Where Rust would earn its keep A single-binary, dependency-free kernel host: ZMTP plus the Jupyter protocol in Rust, driving any CDP target. That's a packaging choice, not a capability gain. It's worth doing only if shipping a Node-based host becomes the obstacle. Revised: the host now also runs on Deno, installed from JSR, and that obstacle hasn't appeared.
09

Risks and gaps

Revised. The original list, with what happened to each item:

  • No comms, so no ipywidgets. Resolved (#9): comms work on every target, with anywidget-style widgets through jupyter.widget. The classic ipywidgets controls are Python classes, so they remain unavailable.
  • Formatting differs on Node. Kept, deliberately (#17): each runtime's users see the format they expect. On a fixture of 30 typical values, 23 format identically on Node and Deno; the rest differ in string quotes and Node's loader frames in stacks. A test fails if a new kind of difference appears.
  • Node npm: is simple. Partly resolved (#14, #39, #40): an opt-in lockfile pins exact versions, and installs are serialized. The cache is still shared, so peer dependencies resolve by real name, and a project's package.json doesn't decide an npm: import's version.
  • Two processes. Unchanged. The inspector is now private to the host, and the workerd and celld sessions are opened with a per-launch token.
  • The interrupt recipe relies on observed V8 inspector behaviour. Pinned: CI checks it on every combination of Node 24/26 and Deno 2.9/latest (#15).
  • Deno targets use --node-modules-dir=none. Resolved (#13): a Deno target honours the notebook's deno.json and project node_modules.
  • Not done: type checking and WebGPU display remain undone. Done: the debugger (#18), on Node and Deno only, and inspect_request content (#10), from runtime values rather than TypeScript types.

New since the first compile:

  • Weakly held inspector promises. With replMode or awaitPromise, V8's inspector holds the result promise only weakly until its callback runs, so a GC in that window fails the call with "Promise was collected". It broke Deno target startup intermittently (#50, fixed by using plain evaluates there). Cell evaluation, several callFunctionOn helpers, comms and the debugger still use those flags (#55).
  • The in-process backends are less faithful. On Bun, workerd and celld, a busy-cell interrupt restarts the runtime and loses state, top-level declarations are globalThis properties, and only a trailing expression shows a result.
  • workerd needs --experimental for UnsafeEval, and its cells share one request that never ends, so production limits don't apply. A Workers project's main is bundled with esbuild directly, not with wrangler's build.
  • Windows isn't supported (#32). Unit tests were made portable, but the workerd target needs Unix sockets, the e2e suite has never run there, npm: installs spawn bare npm (#51), and celld has no Windows build. The Windows CI job was removed until the work is taken up.
  • Little real-world use yet. The suites are broad, but the kernel is new.
10

Recommended next steps

Revised. Four of the five original steps are done:

  1. Promote the spike to its own repo and publish it to npm and JSR. Done: tlockney/cdp-kernel, released as @tlockney/cdp-kernel 0.1.1 through 0.4.0 with npm provenance.
  2. Ship typings for the jupyter global. Done (#11).
  3. Add comms, so ipywidgets and anywidget work. Done for anywidget (#9). The kernel now does something deno jupyter never did.
  4. Offer it upstream. No one has claimed the Jupyter kernel in denoland/deno#36995 or the forks. A runtime-neutral kernel is useful to all of them, and it keeps working whichever fork wins. Open (#16).
  5. Only then consider the workerd hybrid backend or a Bun backend. Done, ahead of step 4: Bun, workerd and celld targets (#7, #8, #25).

What's next from here:

  1. Offer it upstream, as above (#16).
  2. Close the weak-promise exposure in cell evaluation, comms and the debugger (#55).
  3. Get real notebooks run on it, and treat what breaks as the next priority list.
  4. Windows, if users ask for it (#32, #51).

Where it landed

PredictionOutcome
The protocol half and display API port cleanly; CDP is the seamHeld. Node and Deno targets share one bootstrap, and the host now also runs on Deno.

The verdict stands: extract the JS halves and drive the runtime over CDP, with in-process backends where a runtime can't be driven that way.
